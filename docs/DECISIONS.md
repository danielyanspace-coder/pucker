# Pucker — принятые решения

Первоисточник требований к алгоритму — `docs/TZ.md` (ТЗ заказчика).
Здесь зафиксировано то, что ТЗ не покрывает или что уточнено в обсуждении.

## 1. Хрупкость

- Шкала по ТЗ: **1 = максимально хрупкий, чем больше — тем прочнее**.
- Правило: `top.fragility <= bottom.fragility` для физически контактирующих коробок.
- Количество уровней настраивается (2 / 8 / 10). Правило от этого не зависит.
- Файл «Пример» (шкала 1–8) читается в том же направлении. Данные это подтверждают:
  наполнитель 4,5 л, 13,5 кг → 8 (прочный); сухой корм 1,5 кг в мягкой упаковке → 2.
- Режим «хрупкий / не хрупкий»: хрупкий = 1, не хрупкий = максимальный уровень шкалы.

## 2. max_top_load по умолчанию

- Если колонка с допустимой нагрузкой есть в Excel, берём её.
- Если нет, вычисляем из класса хрупкости и площади верхней грани:
  `max_top_load = top_area_m2 × pressure(fragility)`, где `pressure` — таблица кг/м²
  по классам в настройках компании. По умолчанию линейно от 200 кг/м² (класс 1)
  до 3000 кг/м² (класс 10); берётся самая большая грань коробки.
- Компания может отключить ограничение (`use_max_top_load = false`).

## 3. Единицы

- Внутри ядра размеры хранятся в целых мм, вес в кг (float).
- При импорте единицы выбираются в диалоге (по умолчанию см, с автоопределением).
  Перевод идёт с **округлением вверх** до целого мм.

## 4. Устойчивость: запрет «башен» (дополнение к ТЗ, жёсткое ограничение)

Помимо опоры снизу (≥70%, центр тяжести внутри опорного многоугольника) проверяется
боковая устойчивость:

1. **Подпёртая коробка.** Если хотя бы одна боковая грань касается соседа или стенки
   (касание ≥ 20% грани, зазор ≤ 20 мм), коробка считается подпёртой.
2. **Свободностоящая коробка** (соседей нет ни с одной стороны) обязана выдерживать
   наклон 20° (торможение/поворот): для неё и для каждого свободностоящего уровня
   стопки под ней высота над этим уровнем ≤ ширина уровня / tan(20°) ≈ 2,75 × ширина.
3. Отсюда же запрещены высокие узкие коробки «на торце» без соседей.

Пороги в `PackRule`: `tilt_angle_deg`, `lateral_min_contact_ratio`, `lateral_gap_mm`,
`lateral_min_braced_sides`. Проверка отдельная и в движке, и в валидаторе (`TOWER`).

## 4b. Коробки на ребре (по замечанию на 3D-модели)

- Коробка не может стоять выше, чем 3 × её тонкая сторона основания (`max_item_slenderness`).
- «Стоящая» коробка — высота ≥ 2 × тонкая сторона (`standing_ratio`). Ей нужно:
  - опора ≥ 90% площади дна (`standing_support_ratio`) — не на маленькой коробке;
  - соседи или стенки с **обеих** широких сторон, каждая закрыта ≥ 50%
    (`standing_contact_ratio`) — как книга, зажатая на полке. На краю палеты, где сбоку
    пусто, стоять на ребре нельзя.
- Цена правила на «Примере» — около 5 пунктов плотности (≈80% → ≈75%).
- Валидатор: `ON_EDGE`, `STANDING_FREE`.

## 4a. Допуск опоры

Верх коробки, который ниже дна верхней коробки не более чем на `support_tolerance_mm`
(по умолчанию 5 мм), считается опорой: картон проминается на несколько миллиметров.
Без допуска коробки с разницей высот в 1–2 мм (обычная погрешность замеров) не могли бы
служить общей опорой, и плотность падала бы на 10–20%.

## 5. Нехватка места

- **До расчёта** (мгновенно): объём груза больше объёма места; вес больше грузоподъёмности;
  отдельная коробка не помещается ни в одном повороте; мягкое предупреждение, если
  требуемое заполнение выше ~90%.
- **После расчёта:** «Размер пространства не позволяет разместить весь груз», сколько
  коробок, артикулов, м³ и кг не поместилось, причина по каждой коробке, варианты:
  добавить место / выбрать больше / автоподбор.
- Какие коробки оставлять: по необязательной колонке «Приоритет», без неё —
  максимизировать заполнение.

## 5a. Ядро упаковки (реализовано, шаг 1)

- `engine/core` — библиотека на Rust: модели, поиск, метрики, независимый валидатор.
- Поиск — anytime-мультистарт на всех ядрах. Три конструктивных режима:
  - **Sequence**: коробки по очереди (разные сортировки), каждая в лучшую точку;
  - **Fill**: берём самые низкие свободные точки и подбираем под них лучшую коробку;
  - **Layers**: ровные слои из коробок близкой высоты (2D MaxRects), остатки — Fill.
  Половина новых попыток — мутации лучшей найденной, половина — случайные.
- Кандидатные точки — углы верхних граней и боковые углы уложенных коробок с привязкой
  коробки к любому из четырёх углов.
- Сравнение решений лексикографическое (ТЗ §3): всё уложено → меньше мест → меньше
  суммарный объём мест → устойчивость (шаг 0,05) → плотность → меньше свес → ниже.
- Каждый результат перепроверяется валидатором; его ошибки попадают в результат.

## 5b. Время расчёта и качество

- Качество важнее скорости: по умолчанию время зависит от задачи —
  `20 с + 0,5 с × число разных типов коробок + 0,05 с × число коробок`, но не больше 3 минут.
  Разнородный груз (много разных артикулов) думает дольше, одинаковые коробки — секунды.
  Примеры: «Пример» заказчика ≈ 2 мин, 1000 коробок 5 размеров ≈ 40 с, 48 одинаковых — мгновенно.
- Поиск останавливается раньше, если лучшее решение не улучшалось 35% отведённого времени.
- Первое валидное решение появляется за доли секунды (anytime, ТЗ §31).
- Этапы поиска:
  1. фиксированные и случайные старты (три режима построения);
  2. улучшение (ТЗ §32, stage 6): пул лучших решений, перестановки коробок в порядке,
     «разрушить и пересобрать» верх раскладки, смена приоритетов типов коробок;
  3. доводка: при зафиксированном распределении коробок по местам каждое место
     переупаковывается отдельно (25% времени).
- Мягкая оценка устойчивости решает при сравнении только ниже 0,8: выше этого порога
  раскладки считаются одинаково устойчивыми (жёсткие ограничения уже гарантируют
  физическую устойчивость), и выбирается более плотная.
- Можно задать своё время: `time_limit_seconds` с `auto_time = false` (CLI: `--time-limit`).

## 5c. Плотность на «Примере» — что измерено (сентябрь 2026)

- Эталон: PackingSolver (открытый решатель, лучший в своём классе) без требования опоры
  укладывает 341 из 343 коробок в одну палету на 94,5%, но ~105 коробок у него висят
  (опора < 70%). Геометрия набора позволяет много, ограничивают физические правила.
- Наш движок, одна палета, «набить максимум» (среднее по 3 запускам):
  только опора 70% — ~87%; + коробки на ребре только зажатыми с двух сторон — ~76%;
  без этого правила (всё остальное включено) — ~82%. Хрупкость ≈ −4, нагрузка сверху
  (новая таблица) ≈ 0, башни ≈ −1.
- Весь «Пример» на 2 палеты со всеми правилами: 77–78% (время ~2 мин), больше времени
  не помогает — поиск на плато.
- Опробовано и не дало прироста: лучевой поиск по мотивам PackingSolver, блоки
  (Fanslau–Bortfeldt), ровные слои с 2D-раскладкой, послойная по классам оптимизация,
  заглядывание на шаг вперёд, «отложенное» зажатие стоящих коробок, веса штрафов.
- Сработало: последовательное заполнение мест (+2–6), учёт стрейч-плёнки, смешанный
  порядок «размер × прочность».

## 7. Бизнес-модель

- Код принадлежит владельцу проекта; клиенты покупают подписку.
- Онлайн-оплаты нет: оплата по счёту на расчётный счёт. В админ-панели владелец
  вручную ставит компании тариф, срок «оплачено до» и лимиты. После окончания
  срока доступ к расчётам блокируется.
