# Техническое задание
## Разработка алгоритма трёхмерной упаковки грузов

### 1. Назначение

Необходимо разработать с нуля алгоритм трёхмерной упаковки прямоугольных грузов в одно или несколько упаковочных мест.

Алгоритм предназначен для задач, приближенных к реальной логистике:

- размещение товаров на палетах;
- формирование грузовых мест;
- загрузка условных прямоугольных контейнеров;
- подготовка устойчивой компоновки для последующей перевозки.

Все товары и упаковочные места на текущем этапе считаются прямоугольными параллелепипедами.

Основной приоритет алгоритма: не получение математически максимальной плотности любой ценой, а построение физически реализуемой, устойчивой и достаточно плотной укладки.

Целевая плотность упаковки для геометрически подходящих наборов товаров: 85% и выше.

85% не является гарантией для произвольного входного набора, поскольку достижимая плотность зависит от размеров и количества товаров, ограничений по весу, хрупкости, нагрузке и устойчивости.

---

## 2. Область первой версии

Первая версия поддерживает только mixed packing, то есть свободную смешанную упаковку различных SKU.

Не реализуются как отдельные режимы:

- sandwich packing;
- column packing;
- специальные шаблоны упаковки по слоям;
- группировка одинаковых SKU в обязательные блоки.

При этом обычный mixed-алгоритм может естественным образом поставить несколько товаров друг на друга или сформировать локальный слой, если такое размещение оказалось оптимальным и удовлетворяет физическим ограничениям.

---

## 3. Основные приоритеты оптимизации

При конфликте критериев применяется следующий порядок:

1. Физическая допустимость размещения.
2. Устойчивость груза.
3. Отсутствие потенциально опасных конструкций.
4. Максимальная плотность упаковки и минимизация количества используемых упаковочных мест.
5. Скорость расчёта.
6. Минимизация итоговой высоты груза.

Критерии должны применяться преимущественно лексикографически, а не превращаться в один общий weighted score.

Например, увеличение плотности с 87% до 89% не является основанием для выбора менее устойчивой конструкции.

---

## 4. Система координат

Использовать декартову систему координат:

- X: ширина;
- Y: глубина;
- Z: высота.

Начало координат упаковочного места:

(0, 0, 0)

Для палеты:

Z = 0 соответствует нижней поверхности палеты.

Если учитывается физическая высота палеты, товары размещаются начиная с:

Z = pallet.height

Все линейные размеры рекомендуется хранить в миллиметрах.

Вес хранить в килограммах.

Внутри геометрического ядра желательно использовать целочисленные размеры в миллиметрах для уменьшения проблем с floating-point погрешностями.

---

## 5. Модель Item

Каждая физическая единица товара представляется объектом Item.

Минимальный набор полей:

Item
    id: unique identifier
    sku: string

    width: int
    depth: int
    height: int

    weight: float

    fragility: int
    max_top_load: float

### 5.1. Размеры

Размеры задаются до вращения:

width
depth
height

Все товары являются жёсткими прямоугольными параллелепипедами.

Деформация товара не допускается.

---

## 6. Вращение товаров

Товар разрешается поворачивать во всех шести пространственных ориентациях:

W × D × H
W × H × D
D × W × H
D × H × W
H × W × D
H × D × W

Для каждого размещённого товара результат должен содержать выбранную ориентацию.

Если размеры некоторых сторон совпадают, дублирующиеся ориентации необходимо исключать из перебора.

---

## 7. Хрупкость

Каждый товар содержит:

fragility: int  # 1..10

Градация:

1  = максимально хрупкий
10 = максимально прочный

Правило непосредственной установки:

товар сверху может быть установлен на товар снизу только при условии:

top.fragility <= bottom.fragility

Примеры:

1 на 5  -> разрешено
2 на 5  -> разрешено
5 на 5  -> разрешено

5 на 2  -> запрещено
2 на 1  -> запрещено
10 на 1 -> запрещено

То есть более прочный товар не должен размещаться поверх более хрупкого.

Данное правило применяется только между физически контактирующими товарами.

Хрупкость является категориальным ограничением и не заменяет расчёт нагрузки.

---

## 8. Максимальная нагрузка сверху

Каждый товар содержит:

max_top_load: float  # kg

Параметр определяет максимальную внешнюю вертикальную нагрузку, которую товар способен выдержать.

Для каждого размещённого товара необходимо определить суммарную нагрузку, передаваемую на него всеми расположенными выше товарами.

Обязательно:

actual_top_load <= max_top_load

Нагрузка должна учитывать не только непосредственно лежащий сверху товар, но и груз, который этот товар сам поддерживает.

Пример:

A
B
C

Если A стоит на B, а B стоит на C, то C воспринимает вес B и передаваемую через B часть веса A.

---

## 9. Распределение нагрузки между несколькими опорами

Один товар может одновременно опираться на несколько других товаров.

В таком случае его вес и передаваемая сверху нагрузка распределяются между опорами пропорционально площади контакта.

Условно:

load_i =
    total_load *
    contact_area_i / total_contact_area

где:

total_load =
    item.weight + load_received_from_above

Такой расчёт должен выполняться рекурсивно сверху вниз после построения размещения.

Для каждого товара в результате желательно сохранять:

received_top_load
supported_weight
supporting_items
supported_items

Минимальные параметры:

Bin

## 10A. Тип и выбор упаковочного места

Алгоритм должен поддерживать явный выбор типа упаковочного места.

Упаковочное место может представлять:

- палету;
- морской/универсальный контейнер;
- грузовой автомобиль;
- фургон;
- Газель или аналогичный малотоннажный автомобиль;
- железнодорожный вагон;
- другое стандартное транспортное средство;
- полностью пользовательское упаковочное место.

Для первой версии все упаковочные места независимо от реальной формы транспортного средства аппроксимируются прямоугольным параллелепипедом.

То есть ниши, колёсные арки, скосы крыши, выступающие элементы кузова и другие сложные геометрические особенности в V1 не учитываются.

### 10A.1. PackingPlaceType

Рекомендуемый перечень типов:

```text
PackingPlaceType
    PALLET
    CONTAINER
    TRUCK
    VAN
    RAIL_WAGON
    CUSTOM
```

Названия типов не должны влиять на геометрическое ядро алгоритма. Они используются для выбора пресета, UI и применения специфических правил.

### 10A.2. Модель PackingPlace

Рекомендуемая модель:

```text
PackingPlace
    id
    type: PackingPlaceType
    preset_id: string | null
    name: string

    width: int
    depth: int
    height: int

    max_payload: float
    tare_weight: float = 0

    quantity: int = 1

    is_open_top: bool = false

    allow_overhang: bool = false
    max_overhang_x_mm: int = 0
    max_overhang_y_mm: int = 0

    use_pallet_base: bool = false
    pallet: Pallet | null
```

Где:

- `width`, `depth`, `height` — полезные внутренние габариты для размещения груза;
- `max_payload` — максимально допустимый вес размещаемого груза;
- `tare_weight` — собственный вес упаковочного места, если он нужен для расчётов;
- `quantity` — количество доступных одинаковых упаковочных мест;
- `preset_id` — ссылка на стандартный пресет;
- при `preset_id = null` размеры и ограничения задаются вручную.

### 10A.3. Пресеты стандартных упаковочных мест

Система должна поддерживать каталог готовых пресетов.

Примеры категорий пресетов:

```text
PALLET_EUR
PALLET_FIN
PALLET_CUSTOM

CONTAINER_20FT
CONTAINER_40FT
CONTAINER_40FT_HIGH_CUBE
CONTAINER_CUSTOM

GAZELLE_STANDARD
VAN_CUSTOM
TRUCK_CUSTOM

RAIL_WAGON_CUSTOM
CUSTOM
```

Конкретные размеры пресетов не должны быть жёстко зашиты непосредственно в packing-алгоритм.

Они должны храниться во внешнем конфигурационном каталоге или таблице БД и передаваться алгоритму уже как обычный `PackingPlace`.

Это позволит:

- добавлять новые типы машин и контейнеров без изменения алгоритма;
- иметь несколько вариантов одной модели автомобиля;
- корректировать реальные внутренние размеры конкретного кузова;
- использовать корпоративные типы палет и контейнеров.

### 10A.4. Пользовательское упаковочное место

Пользователь должен иметь возможность выбрать:

```text
type = CUSTOM
```

и передать произвольные:

```text
width
depth
height
max_payload
```

Дополнительно:

```text
allow_overhang
max_overhang_x_mm
max_overhang_y_mm
```

Таким образом алгоритм не должен зависеть от заранее известного набора упаковочных мест.

### 10A.5. Палета как самостоятельное упаковочное место

Палета может использоваться двумя способами.

#### Вариант A. Палета является упаковочным местом

Например необходимо сформировать отдельную EUR-палету.

Тогда:

```text
type = PALLET
```

`width` и `depth` соответствуют размерам палеты, а `height` задаёт максимально допустимую итоговую высоту палетированного груза.

Свес может разрешаться настройками `overhang`.

#### Вариант B. Палета находится внутри другого упаковочного места

Например товары сначала формируются на палете, а палета размещается внутри грузовика или контейнера.

Тогда:

```text
type = CONTAINER / TRUCK / VAN / RAIL_WAGON
use_pallet_base = true
```

и характеристики палеты учитываются отдельно.

В V1 допускается упрощённый режим, при котором алгоритм формирует груз непосредственно внутри выбранного PackingPlace либо формирует отдельные палеты. Полноценную двухуровневую оптимизацию «товары -> палеты -> палеты в автомобиль» можно выделить в отдельный следующий этап.

### 10A.6. Несколько доступных типов упаковочного места

Алгоритм должен уметь получать не только один тип места, но и список доступных упаковочных мест:

```text
available_packing_places = [
    PackingPlace(...),
    PackingPlace(...),
    ...
]
```

Например:

```text
2 x GAZELLE_STANDARD
1 x CONTAINER_20FT
5 x PALLET_EUR
```

В зависимости от режима задача может быть двух типов:

```text
FIXED_PACKING_PLACE
```

Пользователь заранее выбрал конкретный тип места, и алгоритм должен использовать только его.

или:

```text
AUTO_SELECT_PACKING_PLACE
```

Алгоритм может выбирать среди разрешённых упаковочных мест.

При автоматическом выборе необходимо стремиться:

1. разместить весь груз;
2. соблюдать все hard constraints;
3. минимизировать количество используемых упаковочных мест;
4. минимизировать суммарный неиспользованный объём;
5. не использовать существенно более крупное место без необходимости.

### 10A.7. Размеры транспортного средства

Для контейнера, фургона, Газели, грузовика или вагона алгоритму должны передаваться именно **полезные внутренние размеры грузового пространства**, а не внешние габариты транспортного средства.

Основные размеры:

```text
inner_width
inner_depth
inner_height
```

Внутри packing engine они могут быть нормализованы до:

```text
width
depth
height
```

### 10A.8. Ограничения загрузочного проёма

Для транспортных средств рекомендуется предусмотреть дополнительные необязательные параметры:

```text
door_width: int | null
door_height: int | null
```

Они нужны для проверки, что груз физически можно внести/загрузить внутрь.

В первой версии проверка загрузочного проёма может быть отключена, но структура данных должна позволять добавить её без изменения API.

### 10A.9. Будущие ограничения

Архитектура PackingPlace должна позволять позднее добавить:

- колёсные арки;
- ниши;
- запрещённые зоны;
- несколько дверей;
- боковую загрузку;
- ограничения нагрузки на оси автомобиля;
- распределение нагрузки по длине кузова;
- крепёжные зоны;
- ограничения конкретного типа вагона.

Эти параметры не входят в геометрическую модель V1.

## 10B. Требование к API выбора упаковочного места

Вход алгоритма должен явно содержать режим и доступные места.

Пример:

```text
PackingRequest
    items: list[Item]

    packing_place_mode:
        FIXED_PACKING_PLACE
        | AUTO_SELECT_PACKING_PLACE

    available_packing_places: list[PackingPlace]

    pack_rule: PackRule
```

Пример фиксированного выбора:

```text
packing_place_mode = FIXED_PACKING_PLACE

available_packing_places = [
    PackingPlace(
        type=CONTAINER,
        preset_id="CONTAINER_20FT",
        quantity=1,
        ...
    )
]
```

Пример пользовательского места:

```text
PackingPlace(
    type=CUSTOM,
    preset_id=null,
    width=2100,
    depth=4200,
    height=1900,
    max_payload=1500,
    quantity=1
)
```

Алгоритм во всех случаях должен работать с нормализованной геометрией PackingPlace, независимо от того, был выбран стандартный пресет или введены пользовательские размеры.

## 11. Палета

Если:

use_pallet = true

дополнительно задаются:

pallet_width
pallet_depth
pallet_height
pallet_weight
pallet_max_payload

Требования:

1. Размер палеты определяет базовую поверхность размещения.
2. Высота палеты входит в итоговую высоту грузового места.
3. Вес палеты входит в полный вес грузового места.
4. Товар располагается поверх палеты.
5. Максимальная нагрузка палеты не должна превышаться.

Таким образом:

total_weight =
    pallet_weight + sum(items.weight)

и:

sum(items.weight) <= pallet_max_payload

а также:

total_weight <= bin.max_weight

## 12. Overhang

Поддержать возможность разрешённого горизонтального выступа товара за границы основания.

Параметры:

allow_overhang: bool

max_overhang_x: int
max_overhang_y: int

Рекомендуемое значение по умолчанию:

allow_overhang = false
max_overhang_x = 0
max_overhang_y = 0

Допустимый конфигурируемый диапазон для специальных сценариев:

0..50 mm

Свес должен рассматриваться алгоритмом как нежелательный.

Если существует два решения одинаковой плотности и устойчивости, должно быть выбрано решение с меньшим overhang.

Вертикальный выход за максимальную высоту не разрешается.

Для полностью закрытого контейнера выступ за внутренние стенки запрещён независимо от настройки палеты.

---

## 13. Минимальная площадь опоры

Любой товар, не расположенный непосредственно на основании, обязан иметь достаточную площадь опоры.

Минимальная доля поддерживаемой нижней поверхности:

min_support_ratio = 0.70

Расчёт:

support_ratio =
    supported_bottom_area / item_bottom_area

Условие:

support_ratio >= 0.70

При расчёте площади необходимо учитывать объединение контактных областей, чтобы одна и та же площадь не учитывалась несколько раз.

---

## 14. Положение центра тяжести отдельного товара

Одной площади опоры недостаточно.

Проекция центра тяжести товара на плоскость XY должна находиться внутри устойчивой области, образованной фактическими точками опоры.

Для однородного прямоугольного товара центр тяжести принимается в геометрическом центре.

Для товара:

center_x = x + width / 2
center_y = y + depth / 2
center_z = z + height / 2

Положение должно проверяться относительно опорного полигона.

Товар с 70% опоры, но с центром тяжести за пределами устойчивой области, считается физически недопустимым.

---

## 15. Запрет опасных мостов

Алгоритм не должен формировать размещения, при которых значительная часть товара висит в воздухе между небольшими удалёнными опорами.

Минимальное требование первой версии:

- support_ratio >= 70%;
- центр тяжести находится внутри опорного полигона;
- опоры распределены таким образом, чтобы товар не опирался только на одну небольшую область у края.

Данный блок должен быть реализован отдельно от обычной проверки коллизий, чтобы впоследствии можно было добавить более точную физическую модель.

---

## 16. Центр масс всего грузового места

Необходимо рассчитывать общий центр масс:

CGx = Σ(mi * cxi) / Σmi
CGy = Σ(mi * cyi) / Σmi
CGz = Σ(mi * czi) / Σmi

Для палеты её собственный вес также желательно учитывать.

Алгоритм должен стремиться размещать общий центр массы:

- ближе к геометрическому центру основания;
- без сильного смещения к одному из краёв;
- по возможности ниже.

Горизонтальное отклонение центра масс является одним из основных показателей устойчивости.

Например:

cg_offset =
    distance(
        load_center_xy,
        base_center_xy
    )

Чем меньше значение, тем предпочтительнее решение.

---

## 17. Тяжёлые товары

Тяжёлые товары должны преимущественно находиться в нижней части упаковки.

Не рекомендуется реализовывать это только через правило вида:

top.weight <= bottom.weight

поскольку оно будет слишком жёстким.

Вместо этого при оценке решения необходимо штрафовать высокий центр массы.

Можно использовать показатель:

vertical_mass_moment =
    Σ(item.weight * item.center_z)

При прочих равных решение с меньшим vertical_mass_moment предпочтительнее.

Дополнительно установка значительно более тяжёлого товара непосредственно на лёгкий товар должна получать штраф, даже если max_top_load формально позволяет это сделать.

---

## 18. Зазоры

Для достижения высокой плотности товары должны иметь возможность соприкасаться.

Поэтому физически обязательный зазор между всеми товарами вводить не следует.

Добавить параметр:

clearance_mm

Рекомендуемый режим:

0..5 mm

Значение должно быть конфигурируемым.

Для сценариев, где технологический зазор не требуется:

clearance_mm = 0

Для сценариев с допусками оборудования:

clearance_mm = 5

Значение 10 мм допускается конфигурацией, но не рекомендуется использовать как стандарт, поскольку на большом количестве небольших коробок оно существенно снизит плотность упаковки.

---

## 19. Коллизии

Два товара не могут занимать общий физический объём.

Для каждой пары размещённых объектов должно выполняться отсутствие пересечения AABB.

Касание граней разрешено при:

clearance_mm = 0

При ненулевом clearance_mm проверка производится с учётом соответствующего расстояния.

---

## 20. Границы упаковочного места

Каждый товар после вращения должен полностью находиться в разрешённой области.

Для закрытого контейнера:

0 <= x
0 <= y
base_z <= z

x + width  <= bin.width
y + depth  <= bin.depth
z + height <= bin.height

Для открытой палеты допускается расширение X/Y на установленный max_overhang.

Высота превышаться не может.

---

## 21. Несколько упаковочных мест

Если все товары не помещаются в одно упаковочное место, алгоритм должен автоматически использовать дополнительные упаковочные места.

Алгоритм должен стремиться:

1. упаковать все товары;
2. не нарушить физические ограничения;
3. использовать минимально разумное количество упаковочных мест;
4. обеспечить плотное заполнение каждого места.

Недопустима ситуация, когда ради небольшого улучшения плотности одного места создаётся большое количество почти пустых дополнительных палет.

---

## 22. Метрики плотности

Необходимо рассчитывать минимум две различные метрики.

### 22.1. Utilization

Для заданного упаковочного объёма:

utilization =
    total_item_volume /
    available_bin_volume

Показывает долю использования всего разрешённого объёма.

### 22.2. Compactness

Для фактически сформированного грузового блока:

compactness =
    total_item_volume /
    occupied_bounding_box_volume

occupied_bounding_box строится вокруг реально размещённых товаров.

Эта метрика позволяет отличать ситуацию:

- товары уложены плотно;
- товары занимают небольшую часть очень высокого контейнера.

---

## 23. Целевая эффективность

Целевой показатель:

>= 85%

для геометрически подходящих наборов товаров.

Основной показатель качества плотной укладки:

compactness

Дополнительно обязательно показывается:

utilization

Нельзя считать алгоритм некачественным только потому, что физически невозможно заполнить 85% заданного контейнера.

Пример:

один товар 500×500×500 в контейнере 1000×1000×1000 физически не может дать 85% utilization.

Поэтому требование 85% должно проверяться на заранее подготовленном benchmark-наборе задач.

---

## 24. Пустоты

Алгоритм должен стремиться минимизировать внутренние пустоты.

Особенно нежелательны:

- вертикальные шахты между товарами;
- крупные внутренние полости;
- узкие недоступные пространства;
- разрозненные товары на верхних уровнях;
- пирамидальная компоновка без необходимости.

При выборе между двумя вариантами с одинаковым используемым объёмом предпочтителен более компактный монолитный грузовой блок.

---

## 25. Flat-top

При прочих равных предпочтительна более ровная верхняя поверхность грузового места.

Следует избегать конструкций вида:

      [ ]
      [ ]
[ ][ ][ ][ ]
[ ][ ][ ][ ]

если существует вариант:

[ ][ ][ ][ ]
[ ][ ][ ][ ]
[ ][ ][ ][ ]

с сопоставимой плотностью.

Ровная поверхность:

- повышает устойчивость;
- уменьшает локальные нагрузки;
- упрощает фиксацию груза;
- уменьшает количество крупных пустот.

Однако минимальная высота остаётся менее приоритетной задачей, чем скорость расчёта согласно установленному порядку критериев.

---

## 26. Оценка устойчивости

Для каждого упаковочного места должен рассчитываться stability_score.

Он может учитывать:

support quality
center-of-mass offset
vertical center of mass
top-load utilization
fragility relationships
overhang
large internal voids
surface irregularity
heavy-item placement

Однако все явные физические ограничения должны оставаться hard constraints.

Нельзя разрешать нарушение max_top_load только потому, что общий stability_score высокий.

---

## 27. Hard constraints

Размещение признаётся невалидным при любом из следующих условий:

1. Пересечение товаров.
2. Выход за разрешённые границы.
3. Превышение максимальной высоты.
4. Превышение максимального веса.
5. Превышение допустимого overhang.
6. support_ratio < 0.70.
7. Неустойчивое положение центра тяжести.
8. Нарушение правила fragility.
9. actual_top_load > max_top_load.
10. Превышение грузоподъёмности палеты.

Невалидное решение не должно участвовать в сравнении с валидными решениями.

---

## 28. Soft constraints

Критерии оптимизации среди валидных решений:

- центр массы ближе к центру;
- центр массы ниже;
- тяжёлые товары ниже;
- меньший overhang;
- меньше внутренних пустот;
- более ровная верхняя поверхность;
- выше compactness;
- выше utilization;
- меньше упаковочных мест;
- меньше итоговая высота.

---

## 29. PackRule

Основные настройки алгоритма рекомендуется объединить в структуру:

PackRule
    min_support_ratio: float = 0.70

    allow_overhang: bool = false
    max_overhang_x_mm: int = 0
    max_overhang_y_mm: int = 0

    clearance_mm: int = 0

    use_fragility: bool = true
    use_max_top_load: bool = true

    target_compactness: float = 0.85

    optimize_center_of_mass: bool = true
    prefer_heavy_items_below: bool = true
    minimize_voids: bool = true

    time_limit_seconds: int = 300

    random_seed: int | None

В будущем структура должна допускать расширение дополнительными правилами без переписывания геометрического ядра.

---

## 30. Масштаб задачи

Типичная задача:

~500 физических товаров

Максимальная ожидаемая задача первой версии:

~2000 товаров

SKU могут повторяться.

Необходимо избегать полного перебора вариантов размещения.

Количество возможных последовательностей и ориентаций делает exhaustive search практически неприменимым.

---

## 31. Ограничение времени

Максимально допустимое время поиска для крупных задач:

300 секунд

Алгоритм желательно проектировать как anytime algorithm.

То есть:

1. быстро построить первое валидное решение;
2. сохранить его как best_solution;
3. продолжать улучшение;
4. при достижении time_limit вернуть лучшее найденное валидное решение.

Алгоритм не должен терять весь результат из-за достижения тайм-аута.

---

## 32. Рекомендуемая архитектура алгоритма

Конкретная эвристика не является жёсткой частью ТЗ, однако рекомендуется следующая архитектура.

### Stage 1. Preprocessing

- валидация входных данных;
- раскрытие quantity в физические экземпляры либо работа через оптимизированные группы;
- генерация уникальных ориентаций;
- расчёт объёмов;
- классификация товаров по размерам, весу и хрупкости.

### Stage 2. Initial sorting

Формирование нескольких вариантов порядка товаров, например:

- объём по убыванию;
- площадь основания по убыванию;
- вес по убыванию;
- комбинация volume + weight + fragility.

Не следует использовать только один фиксированный порядок.

### Stage 3. Candidate points

Не перебирать все координаты пространства.

Использовать конечное множество перспективных точек размещения, например:

- extreme points;
- corner points;
- maximal empty spaces;
- поверхности уже размещённых объектов.

### Stage 4. Feasibility check

Для каждой кандидатной позиции проверять:

- boundary;
- collision;
- support;
- center of gravity;
- fragility;
- top load;
- total weight.

Невалидные кандидаты отбрасываются сразу.

### Stage 5. Candidate scoring

Среди валидных кандидатов предпочтение отдаётся позициям:

- ниже;
- ближе к существующему грузовому блоку;
- закрывающим пустоты;
- увеличивающим площадь контакта;
- не смещающим центр массы;
- не создающим высокий локальный выступ.

### Stage 6. Improvement

После получения первичного решения выполнять улучшение:

- изменение порядка части товаров;
- перемещение товара;
- изменение rotation;
- перестановка товаров;
- перенос между палетами;
- repacking локальной области.

Можно использовать:

- multi-start;
- beam search;
- GRASP;
- local search;
- simulated annealing;
- другие метаэвристики.

Главное требование: укладываться в установленный time budget.

---

## 33. Работа с одинаковыми SKU

При наличии большого количества одинаковых товаров алгоритм не должен полностью игнорировать повторяемость.

Разрешается использовать ускорения:

- кэширование допустимых ориентаций;
- кэширование геометрических проверок;
- группировку идентичных кандидатов;
- batch placement;
- symmetry reduction.

При этом формально результат должен содержать координаты каждой физической единицы.

Результат должен содержать:

calculation_time
iterations
solutions_checked

Это необходимо для:

- профилирования;
- воспроизводимости;
- сравнения версий алгоритма;
- автоматического benchmark-тестирования.

---

## 38. Валидатор

Финальный результат должен проходить отдельный независимый validator.

Validator повторно проверяет:

collision
bounds
weight
height
support
fragility
top load
center-of-gravity stability
pallet payload

Search engine и validator желательно разделить архитектурно.

Это позволяет избежать ситуации, когда ошибка внутри эвристики одновременно создаёт и «проверяет» неправильное размещение.

---

## 39. Benchmark

До оптимизации алгоритма необходимо создать фиксированный набор тестовых задач.

Минимум:

### Геометрические тесты

- одинаковые коробки;
- несколько размеров коробок;
- большое количество мелких коробок;
- смесь крупных и мелких;
- товары, почти совпадающие с размером палеты.

### Весовые тесты

- тяжёлые и лёгкие;
- тяжёлые товары должны уходить вниз;
- превышение max_weight.

### Fragility tests

- 1 нельзя использовать как основание для 2;
- 2 можно ставить на 5;
- несколько уровней fragility.

### Top-load tests

- допустимая нагрузка;
- нагрузка точно на границе;
- превышение;
- передача нагрузки через несколько уровней;
- распределение нагрузки между двумя опорами.

### Stability tests

- 100% support;
- 70% support;
- 69% support;
- центр тяжести внутри опоры;
- центр тяжести за пределами опоры.

### Overhang tests

- 0 мм;
- допустимый выступ;
- выступ ровно на границе;
- превышение допустимого значения.

### Scale tests

100 items
500 items
1000 items
2000 items

## 40. Критерии приёмки

Алгоритм первой версии считается соответствующим требованиям при выполнении следующих условий.

### Корректность

Для всех решений:

0 collisions
0 boundary violations
0 weight violations
0 fragility violations
0 max_top_load violations
0 support violations

### Устойчивость

Каждый товар:

support_ratio >= 0.70

и имеет устойчивое положение центра тяжести.

Общий центр массы не должен иметь неоправданного сильного смещения к краям при наличии альтернативного размещения.

### Плотность

На benchmark-наборах, где плотность 85% объективно достижима без нарушения физических ограничений, алгоритм должен стремиться к:

compactness >= 0.85

### Производительность

Алгоритм должен поддерживать задачи до:

2000 items

и соблюдать установленный:

time_limit <= 300 seconds

При истечении времени возвращается лучшее найденное валидное решение.

---

## 41. Что сознательно не входит в V1

В первую версию не включаются:

- цилиндрические товары;
- неправильные формы;
- мягкие и деформируемые упаковки;
- sandwich packing;
- отдельный режим column packing;
- физическая симуляция движения автомобиля;
- расчёт трения;
- динамические ускорения при торможении и поворотах;
- прочность картона как материала;
- давление в Па на контактную поверхность;
- крепёжные ремни и стрейч-плёнка;
- ML/RL-модели.

Архитектура должна позволять добавить эти возможности позже.

---

## 42. Главный принцип

Алгоритм должен решать не классическую задачу:

«Как геометрически засунуть максимальный объём параллелепипедов в другой параллелепипед?»

а более прикладную задачу:

«Как сформировать максимально плотное грузовое место, которое можно физически собрать, переместить и перевезти без очевидно неустойчивых или разрушающих груз конструкций?»

Поэтому геометрическая плотность является важной, но не главной характеристикой.

Приоритет первой версии:

VALID
↓
STABLE
↓
SAFE
↓
DENSE
↓
FAST
↓
LOW
